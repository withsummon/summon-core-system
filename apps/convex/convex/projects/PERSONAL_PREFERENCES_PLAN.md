## Current frontend feeders

1. `services/project/project.service.ts` GET/PATCH user-properties; `store/issue/project/filter.store.ts` reads and updates `rich_filters`, `display_filters`, and `display_properties`. Those settings change actual issue fetch/group/pagination and layout, not merely saved metadata.
2. `store/project/project.store.ts:updateProjectView` sends only `sort_order` through that same service. `components/workspace/sidebar/projects-list.tsx` computes a drop position, writes personal order, and retains all other properties. `ProjectMember.save` / member-add / invitation acceptance initialize ProjectUserProperty; regular member addition prepends by minimum order minus 10000 (first 65535), while bulk invitation creation uses model defaults.
3. `store/member/project/base-project-member.store.ts` also reads/writes **ProjectUserProperty**, despite its member-store name. `components/navigation/use-tab-preferences.ts` reads `preferences.navigation.default_tab/hide_in_more_menu`; sidebar project links, project-header selection and `tab-navigation-root` actually consume it.
4. Navigation keys: work_items, cycles, modules, views, pages, intake, overview, epics. Defaults are work_items and no hidden tabs. `preferences.pages.block_display` defaults true in Django, is preserved by navigation writes (frontend fallback false if missing); no current page-layout consumer found by repository search.
5. Native `projects.index.list` currently returns current member's active projects without personal sorting. `core-workspace.tsx` chooses a project by identifier and renders hardcoded task/cycle/module/intake/view/settings tabs. It has no personal project order or navigation preference owner. Existing workspace sidebar preferences in `navigation` are a distinct workspace-level contract and must not be repurposed.

## Proposed coordinated native slice

Use one private project-user property owner keyed `(projectId,userId)`, with workspaceId derived from project; separate typed columns for personal project order and navigation preferences plus one captured revision. Do not create a general JSON settings bag or duplicate task filter evaluator. Reads/writes require current workspace **and** project membership, including guests for personal settings; never accept a target user ID. Administrator status grants no access to another user's preferences. Archived-project behavior must remain read-only until a specific legacy route exception is proven.

First independently deliverable closure: personal project ordering, with a real ordered chooser/list consumer. Add indexed `(workspaceId,userId,sortOrder)` rows, preserve deterministic tie handling, and initialize through existing canonical project creation/grant owners. Existing membership population needs a bounded, repeatable initialization migration before making the required row an invariant. Parent should coordinate both-host backfill and final read cutover; do not hide missing rows with perpetual fallback. Preserve ordering on revoke/rejoin while withholding inaccessible targets. Reorder must operate on current authorized project neighbors and captured revision, with explicit bounded-scan failure (not an apparent first/last position based on a partial page). Concurrent reorder must remain atomic; finite representable order and equal-neighbor resolution need tests.

Second coordinated closure can add typed personal navigation choices to that same owner and make native project links/header/tab overflow honor them. Only enable options with real native destinations; pages/epics/standalone overview routing remains explicit until those consumers exist. Settings is a native administration tab, not a legacy default-tab key. Hiding must move a tab into an accessible More menu, not remove navigation. Explicit deep links override default-tab preferences; project switching clears only stale entity selectors and applies the selected project's default. Do not expose a preference editor that persists unsupported navigation keys without functioning routes.

Task `rich_filters`, grouping, order, layout and display-property settings are another implementation stage **within this canonical owner**, coupled to actual task result/render owners. Current savedViews typed filter validator/evaluator can be reused for its supported subset, but does not implement inherited nested rich-filter DSL, kanban/calendar/spreadsheet/group pagination. Do not label a metadata-only persistence endpoint as this parity.

## Acceptance required

- Two users have independent ordering/navigation; guest can change own; outsider, revoked workspace/project member, and admin targeting another user denied. No inaccessible project name or preference disclosure during pagination.
- New project/member initialization, old membership bounded migration twice, revoke/rejoin retention, archive exclusion and unarchive order retention.
- Captured revision conflicts, concurrent neighbor changes, finite numeric validation, duplicate positions and beginning/end movement across page boundaries without silent truncation.
- Real list/project chooser uses server ordering and reacts across tabs; default tab applies on project selection, explicit deep links survive, hidden tab remains reachable in More, all enabled destinations exist.
- Every unimplemented registered endpoint and legacy rich-layout feature stays in the closure ledger; no Django removal is authorized by this proposal.
