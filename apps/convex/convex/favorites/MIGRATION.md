# Native personal favorites: additive transition

Legacy owners: `plane/db/models/favorite.py`, `app/views/workspace/favorite.py`, `app/serializers/favorite.py`, web `store/favorite.store.ts` and `components/workspace/sidebar/favorites`. Actual entity types are project, cycle, module, view, page, issue, folder. Nullable name, descending sequence, folder parent and per-user entity uniqueness are retained. Native page targets refer to documents and issue targets to tasks; no legacy UUID mapping is implied. Legacy issue entity_data is null; native task name projection is an explicit richer native contract.

Current workspace administrators/members can manage only their own favorites; workspace guests cannot read/write this shell collection, matching the inherited endpoint. Existing project saved-view favorites additionally forbid project guests, and workspace saved-view favorites forbid workspace guests. Their public consumers remain on the old owner during this additive stage.

New favorites store typed targets, not copied target names. Every list page resolves current visibility through existing projectReader, taskCanRead, canAccessDocument and saved-view capability owners. Hidden targets emit no favorite alias or target title; sparse pages preserve cursor/isDone. Project membership remains required even for workspace admins. Archived project targets hide; readable archived task/cycle/module targets follow their current owners. Folder metadata stays author-private.

Tree writes reject cycles and depth above20 explicitly. Persisted subtree height and parent-height index validate moving a whole subtree without descendant scans. Height includes trashed descendants so restoration cannot create an over-depth tree. Each change updates at most20 ancestor heights. Folder trash retains descendants; ancestor trash hides child collections and blocks descendant edits until restoration. Individual child trash remains individual. This intentionally replaces inherited permanent folder cascade with recoverable native lifecycle. Ordering is finite numeric descending, stable index tie-breaking; new rows allocate above the current author's selected folder maximum, avoiding legacy cross-user sequence coupling. Names up to255 preserve null/empty spelling. Updates/lifecycle use monotonic captured revisions.

## Saved-view migration and activation

Old savedViewFavorites readers/writers remain canonical. New generic view-target mutations are explicitly unavailable during the transition. Internal backfill copies their immutable view/user/workspace identity, original creation order, and source ID idempotently. Reconcile removes migrated rows whose source disappeared. Deploy additive schema/functions first, scan both hosts. Under a short old-writer freeze, rerun backfill and reconcile to completion and verify zero additional changes plus matching source/destination identities. Only then switch existing saved-view flags/lists/writers to the shared owner in one coordinated release and remove the view-write transition gate. There is no dualwrite.

After both hosts verify new owner reads/writes, remove old table and legacySourceId metadata via bounded cleanup, then remove obsolete migration entrypoints. Do not remove the source table while schema IDs still reference it. New per-user folder metadata is not used by old consumers before activation. No legacy route or sidebar has been cut over by this backend stage.

Recent visits and sidebar preferences remain separate: legacy visits return latest20 issue/page/project records with guest access and producers elsewhere; preference keys include views, active_cycles, analytics, drafts, your_work, archives and stickies, with seeded pinned defaults and ascending sort_order. They are not replaced by favorites.

Additive source is activated; six module-owned behavior tests, native TypeScript7 and scoped Oxlint pass. Tests include privacy, ancestor trash/recovery, depth/cycle rejection, subtree moves, sparse visibility, idempotent migration and captured revisions. No deploy or runtime acceptance is claimed.

`state` uses effective ancestor visibility for entity header flags; re-adding a retained favorite under trash explicitly requests parent recovery instead of silently returning an invisible entry. Restore checks target canFavorite as well as visibility. View state remains gated until coordinated cutover.
