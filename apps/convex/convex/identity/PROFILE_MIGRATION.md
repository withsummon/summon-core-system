# Account profile slice

## External user identity rollout

The inherited `GET /api/v1/users/me/` publishes a persistent UUID. Native application `users.apiId` owns that external identity separately from the Convex record ID and Better Auth component user ID. The existing user owner allocates a native UUID, parses it through `apiIdSchema` and checks its indexed uniqueness inside the creation transaction. Both configured authentication insertion paths use it; linking, profile editing and email changes retain the same ID. No response-generated ID or generic identity registry is introduced.

Application User, Project and Workspace UUID fields are required. The completed additive rollout used the canonical missing-only mutations and full second scans with zero changes: local user coverage plus 143 Project/133 Workspace rows, then genuine creation/lifecycle proof; remote two Users/one Project/two Workspaces with every other field and stored byte unchanged. The temporary backfill mutations and incomplete-identifier response are removed from current source. Exact source/runtime receipts and the required-schema activation gates are recorded in the [migration checklist](../../../../docs/migrations/convex/current-parity-checklist.md). Older deployments need their own complete UUID coverage proof before upgrading to this required schema. Optional-UUID source `f110789ef0` includes the four Project provenance fields and the verified-email recovery source fix; it is a rollback candidate only after fresh complete-row schema validation and review of its exact module, auth and environment contracts. Preserve every UUID and never import an older snapshot over subsequent writes. Reads never allocate, regenerate or substitute a Convex ID.

The external user transport has separate scoped integration receipts for API-key verification, inherited user fields, authenticated current-avatar bytes, quota/error headers and safe audit logging. Required-schema activation, native-auth/frontend cutover and remaining external API parity are separate gates; this source cleanup does not claim them complete.

Legacy owner: UserEndpoint and UserSerializer first/last/display name and timezone fields. Native owner: identity/profile with implicit Better Auth identity and a verified link to the stable application user; no user ID is accepted from the caller. Application users.name remains the public display-name field. Private first/last/timezone metadata lives in userProfiles indexed by user; both records change atomically. Missing profile means a not-yet-configured account with revision 0, not a migrated credential.

Names are bounded and first/last names reject URL-shaped input. Timezone uses existing settings/timezone validation. Every save captures a revision; concurrent insertion/update conflicts cannot overwrite a newer profile. Frontend uses established fields in Account details; its draft is keyed by identity, never by live revision. Review caught and fixed missing identity-key isolation.

Historical pre-native-auth evidence covered a profile save and stale draft rejection on a local development server. The earlier five-test count describes that previous checkpoint, not a retained test portfolio or the current candidate. The migration test files were removed at the user's request. Current isolated runtime checks cover profile/preferences CAS, required onboarding first name, optional General personal names, atomic empty-display-name denial and stable native identity. Current browser acceptance must identify its actual served build and route; an earlier viewport's document width does not prove that the current form fits within it.

Scope remaining: timezone is profile metadata; timestamp presentation still uses existing browser/project behavior. The [native account boundary](../../../../docs/migrations/convex/better-auth-candidate.md) records candidate preference/onboarding/image and credential/session ownership, local evidence and open email/OAuth/cutover gates. Legacy endpoints remain until all consumers and those contracts migrate. Local development observations do not establish a production rollout.

## Shared profile-image slots

`identity.avatar` now owns both avatar and cover slots through the same upload, removal and recovery operations. The public slot enum is reused from `assets/schema`; stored avatarAssetId, avatarUserId, avatarRevision and avatarPublishedRevision retain their names so existing native avatars continue to read without a renaming adapter. Optional coverAssetId/externalCoverUrl mean an existing account has no configured cover. File metadata validators are shared by the assets table and asset, personal-image and project-cover preparation boundaries.

Cover preparation and finalization reuse `prepareAsset` and `assets.upload.finalize`, including signature/digest validation, owner access rechecks and profile revision comparison before publication. The existing upload receipt acknowledges either slot. Replacement/removal retain the former blob for seven days, and recovery checks current identity, slot purpose, retention and storage existence before replacing the pointer. A missing referenced asset is an invariant error. Member avatar descriptors include the workspace read context required by the private byte endpoint. External cover selection reuses the asset-content URL owner, accepts no credentials or non-http/https scheme, and soft-removes the replaced upload in the same profile transaction.

The controlled `ImagePickerPopoverView` lives in the existing picker module and uses the existing cover presets, tabs and dropzone. Its native path invokes no legacy user/instance store, SWR or FileService; those stay in the adapter for currently registered project consumers. Native preset selection uploads bundled image bytes through the same asset pipeline rather than persisting build-specific frontend URLs. The browser object URL is revoked on replacement/unmount, preset tiles are keyboard buttons, and failed selection retains the open picker. Unsplash remains an optional provider capability; no native provider is fabricated when absent. These are source contracts; restored byte delivery, full modal journeys, role/isolation behavior and deployed visual parity still require runtime/Chrome acceptance.
