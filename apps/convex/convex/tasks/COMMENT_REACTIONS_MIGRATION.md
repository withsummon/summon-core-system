# Internal comment reactions

Legacy `app/views/issue/comment.py:CommentReactionViewSet` allows active project admin/member/guest reactions, lists newest-first and removes only the caller's reaction code. `CommentReaction` enforces active uniqueness on comment/actor/reaction. The native owner is `tasks/commentReactions.ts`, with required taskId and commentId checked together so an old component cannot submit a comment from another task.

`access({taskId,commentId})` returns canReact. `list({taskId,commentId,paginationOpts})` returns bounded actor rows with actorName/isMine, preserving the standard cursor. `set({taskId,commentId,reaction,active})` derives the actor from current authentication and is idempotent for the requested state. Reaction codes reuse the task reaction's bounded decimal Unicode scalar encoding, including control/surrogate rejection. Arbitrary legacy text codes are not silently imported.

Both task and comment endpoints now reuse `reaction_owner.ts` for code validation, actor display projection and the actual actor-state transition. The small typed writer is used by two concrete table owners: lookup/insert remain table-specific, while no-op detection, tombstoning and canonical taskChanged event transaction have one implementation. It does not perform authorization; each endpoint first resolves its actual task/comment and current caller. Existing task reaction public arguments and return shape remain unchanged.

The canonical task access owner governs workspace/project membership and guest visibility. Deleted comments reject all reaction reads and changes, including by their author; reactions are retained and reappear when the comment is restored. Archived tasks permit reads but no reaction changes. Deleted/triage tasks and archived projects remain inaccessible. Readers cannot change another actor's reaction, and there is no admin impersonation path. Reaction changes do not replace comment text or increment its content revision; they update canonical task revision/activity only. Duplicate desired state does neither.

Lists read at most 100 candidates/1 MiB. They report individual actor rows, not an incomplete aggregate count. Generic updated task events reuse current recipient authorization; full legacy comment-reaction activity wording/payloads, email channels, public-board reactions/votes and REST aliases remain separate parity work. This implements internal comments only and does not retire Django controllers.

Four module BDD scenarios cover actor uniqueness and independent task/comment targets; guest-policy changes and revocation; deleted-comment hiding/restoration and cross-task ID rejection; archived-read-only and shared validator/page limits. The existing seven task reaction/link scenarios also pass after sharing the writer. Native TS7, scoped Oxc and complexity <=10 pass. Browser and deployment acceptance are parent-owned and not claimed by these tests.
