# Atomic selected-task cycle/module membership

Actual inherited controllers exist: app cycle/issue.py CycleIssueViewSet.create receives issues, scopes workspace/project, moves existing one-cycle links and creates new links, rejects completed target. ModuleIssueViewSet.create_module_issues adds same-project links with conflict-ignore semantics. These are the concrete membership contracts; no registered bulk-operation-issues generic property controller was found. Completed-source transfer/progress snapshots remain their separate legacy owner.

Native tasks.bulk_memberships.change accepts project,1–20 distinct task IDs/captured revisions, one typed cycle/module ID+captured metadata revision and assigned boolean. Current project writer and active-task access/project/revisions are validated before applying changes. Canonical assignCycleTask, extracted unchanged removeCycleTask, and setModuleTask own actual membership mutation, capacity, lifecycle and task event behavior. Calls execute sequentially inside one Convex transaction, so cycle capacity checks observe earlier writes; a later rejection rolls back every edge, task revision and event. Already-assigned no-op still requires current per-task captured revision at bulk boundary.

Cycle assignment moves existing links and keeps stable task identity. Module assignment is additive and leaves other modules/cycle untouched. Removal targets only the selected owner; it is not clear-all. Active selected tasks only: retained inactive-link cleanup remains existing individual owner flow. Existing source-cycle completed/archive restrictions apply; transfer is not implemented by bypassing those checks.

Four new BDD plus17 existing cycle/module tests pass: successful assign/remove, additive independent memberships, stale batch rollback, archived target rejection, and99-existing-task capacity with a later batch failure rolling back first insertion/revision. Foreign-project target, guest and revoked-project public boundary rejection are also covered. Native TS7 and scoped Oxc pass. No deployment/UI claims. Same static20-task event fanout budget as bulk lifecycle applies; capacity is not benchmarked.
