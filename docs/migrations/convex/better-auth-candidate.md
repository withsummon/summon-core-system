# Better Auth candidate boundary

The native Better Auth component is installed alongside the existing Convex Auth data, but only one JWT issuer can serve the `convex` audience at a time. `SUMMON_AUTH_ENGINE=convex-auth` keeps the existing provider and `/api/auth` routes; `SUMMON_AUTH_ENGINE=better-auth` selects the component provider and `/api/better-auth` routes. Both the deployment environment and the CLI environment must select the same mode when pushing code. Remove this selector after the account cutover is accepted.

The app's `users` IDs remain the owner of memberships, authored content and permissions. `betterAuthLinks` maps a Better Auth user to an app user only after Better Auth verifies its email. The trigger rejects ambiguous verified emails, already linked users and deactivated accounts. The product access boundary checks the live component session, link, verified email, app user and restriction before returning a user. The component reuses the existing Resend sender for encrypted-at-rest OTP messages; it cannot deliver account mail until `AUTH_RESEND_KEY`, `EMAIL_FROM`, `SITE_URL` and `BETTER_AUTH_SECRET` are configured.

Local candidate proof on 2026-09-28: component deployment succeeded, `GET /api/better-auth/ok` returned 200 and unauthenticated `GET /api/better-auth/get-session` returned 200 with `null`. An unauthenticated workspace query returned `SESSION_EXPIRED` through the app's account boundary. The local deployment was then restored to `SUMMON_AUTH_ENGINE=convex-auth`; the legacy JWKS endpoint returned 200 and the candidate path returned 404. Native TypeScript 7 and Oxlint passed. No account was created or migrated in this proof.

Before the candidate can own a product route, import the existing remote users and any credential hashes through an operator-controlled, verified mapping; migrate account settings, password/email change, sessions, deactivation, MCP step-up and protected HTTP routes; mount the Better Auth React provider and sign-in/recovery UI in the preserved shell; configure and send real Resend mail; test verified signup, sign-in, reset, OAuth and revocation in Chrome; then repeat across workspaces. Existing sessions must reauthenticate at cutover. The remote deployment still uses Convex Auth, and Django remains required for the inherited routes.
