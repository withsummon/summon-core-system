# Better Auth candidate boundary

The native Better Auth component is installed alongside the existing Convex Auth data, but only one JWT issuer can serve the `convex` audience at a time. `SUMMON_AUTH_ENGINE=convex-auth` keeps the existing provider and `/api/auth` routes; `SUMMON_AUTH_ENGINE=better-auth` selects the component provider and `/api/better-auth` routes. Both the deployment environment and the CLI environment must select the same mode when pushing code. Remove this selector after the account cutover is accepted.

The app's `users` IDs remain the owner of memberships, authored content and permissions. `betterAuthLinks` maps a Better Auth user to an app user only after Better Auth verifies its email. The trigger permits an existing verified app user to establish a Better Auth identity even when new signups are disabled, and rejects ambiguous, unverified, already linked or deactivated app users. It cannot create a duplicate app user for an unverified email collision. A verified Better Auth email update now keeps the linked app user ID and changes its email in the same component mutation, rejecting an app-user collision or a stale old email. This trigger is typed and source-reviewed, not a tested email-change journey; the UI remains disabled until session revocation and real mail are accepted. The product access boundary checks the live component session, link, verified email, app user and restriction before returning a user. The component reuses the existing Resend sender for encrypted-at-rest OTP messages; it cannot deliver account mail until `AUTH_RESEND_KEY`, `EMAIL_FROM`, `SITE_URL` and `BETTER_AUTH_SECRET` are configured.

An unauthenticated workspace query returned `SESSION_EXPIRED` through the app's account boundary. The shared session owner now validates the linked app user and the component session expiration for `identity.session.status`, which also guards assistant and asset HTTP routes. Candidate mode returned `{ "valid": false }` for an anonymous session, then the local deployment was restored to `SUMMON_AUTH_ENGINE=convex-auth`; the legacy JWKS endpoint returned 200 and the candidate path returned 404. A signed-in existing Convex Auth Chrome session loaded the Modules route after restoration. Native TypeScript 7 and Oxlint passed. No Better Auth account was created or migrated in this proof.

The Convex plugin must advertise the same `/api/better-auth` base path as the HTTP router and issuer config. The 2026-09-28 isolated restore rehearsal deployed this corrected path in Better Auth mode: `/api/better-auth/ok` and `/api/better-auth/convex/jwks` returned 200, while the old `/api/auth/convex/jwks` returned 404. The isolated deployment was returned to Convex Auth mode after the check. This proves route configuration only; it does not prove a verified Better Auth account, session, recovery email or browser journey. The remote issuer and frontend still use Convex Auth.

Before the candidate can own a product route, import the existing remote users and any credential hashes through an operator-controlled, verified mapping; migrate account settings, password/email change, sessions, deactivation and MCP step-up; mount the Better Auth React provider and sign-in/recovery UI in the preserved shell; configure and send real Resend mail; test authenticated assistant and asset HTTP requests, verified signup, sign-in, reset, OAuth and revocation in Chrome; then repeat across workspaces. Existing sessions must reauthenticate at cutover. The remote deployment still uses Convex Auth, and Django remains required for the inherited routes.
