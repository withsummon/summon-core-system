# Draft attachments and content revisions

The task attachment upload, authenticated download, row rendering, and captured-revision lifecycle controls are reused by the draft attachment controller. The controller owns only draft-specific generated queries/mutations and pending-upload reservations. There is no second file validation/hash/upload/finalize state machine. Existing MIME/size policy and bounded blob URL lifetime remain at their current owners.

The draft editor and attachment section are siblings under a stable detail owner. Saving or cancelling content edits does not remount an in-flight attachment transfer; attachment subscription updates do not replace the opened editor state. Attachment access errors have a local boundary so they cannot discard unsaved text. Draft deletion/publication removes attachment access through canonical lifecycle state.

Draft content saves capture `contentRevision`; attachment changes advance aggregate `updatedAt` for publish/copy confirmation without changing the text-save revision. No frontend revision substitution or automatic retry is performed. Pending uploads must finish or be explicitly cancelled before publication. The canonical copy action copies ready files into independent bytes and excludes removed files; the confirmation states that scope.
