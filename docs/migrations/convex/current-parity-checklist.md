# Current Convex retirement checklist

Source snapshot: 2026-09-28, `5cabc8077e` plus the preserved dirty working tree. This is an **open acceptance checklist**, not proof of parity. The [registered surface](registered-surface-2026-09-28.tsv) lists each source registration, its current owner, its acceptance family, and its source line. `OPEN` means no route-wide production-browser acceptance has been recorded. Historical module receipts can establish smaller implemented operations but do not close an entire family.

## Scope and acceptance rule

Every inherited Plane feature remains in scope. The deployed UI is the visual baseline. Each registered route must open under its intended role, complete its reads and writes, exercise its dialogs and commands, show denial/recovery correctly, preserve visible layout and accessibility, and produce a Chrome network capture without Django requests. For external HTTP APIs, compare method, authentication, status, payload, pagination, idempotency, error, and permission contracts with an actual client. For jobs, compare schedule, side effects, retries, and observability. Mark a row accepted only with the exact served build, URL, test actor, artifacts, and rollback record.

The source extraction found **109 web entries** (106 `route`, three `index`) across web/admin/public-space apps, **435 Django endpoint declarations**, ten Django URL mounts, three optional schema/debug declarations, **91 literal Power K command IDs plus two native Stickies commands**, 178 static JSX dialog mounts, **12 Celery beat jobs**, and three Convex crons. The React Router `routes --json` manifest resolves **108 active route/index entries** in either `SUMMON_STICKIES_ROUTE_OWNER` mode; every active path and resolved module matches the ledger, with exactly the alternate `/:workspaceSlug/stickies` module inactive. Run `pnpm exec react-router routes --json` from each of `apps/web`, `apps/admin`, and `apps/space`, and repeat the web command with `SUMMON_STICKIES_ROUTE_OWNER=convex` to reproduce this source-build check. The web `*` routes and Django include mounts are listed intentionally. Dynamic dialogs and keyboard/context actions still need runtime mounted-call review; a local route manifest does not prove the production-served build. The previous 48-pattern Summon list remains a subset of the 435 Django endpoints.

## Better Auth owner migration

The requested owner is the [Convex Better Auth component](https://labs.convex.dev/better-auth/framework-guides/react), with Better Auth storing sessions and accounts inside Convex and `useConvexAuth()` gating protected UI after token validation. The current owner is `apps/convex/convex/auth.ts` plus `identity/session.ts`, `identity/user_owner.ts`, `schema.ts`, `mcp/stepUp.ts`, and `apps/web/core/components/convex-core/provider.tsx`; it uses `@convex-dev/auth` tables and session IDs. Replacing only the provider would invalidate app-user foreign keys, live-session revocation, account restrictions and MCP step-up. The cutover must preserve the app `users` IDs through an explicit Better Auth user mapping and migrate or reset credentials through a verified flow. Keep old session writes available until new account and session behavior passes the identity/account journeys, then remove the old tables/patch and update generated types. The official integration documents [component registration and cross-domain React setup](https://labs.convex.dev/better-auth/framework-guides/react), [validated session authorization](https://labs.convex.dev/better-auth/basic-usage/authorization), and [local installation for custom auth schemas](https://labs.convex.dev/better-auth/features/local-install). No dependency or auth owner was switched by this inventory.

Dependency and credential research on 2026-09-28: the installed Convex CLI is `1.46.0`, and `@convex-dev/better-auth@0.12.5` accepts it with `better-auth@1.6.33` (the `1.7.x` line is outside that component's peer range). Installed Convex Auth uses Lucia scrypt for passwords. Source inspection of both installed Lucia and the pinned Better Auth package found the same NFKC normalization, 16-byte hexadecimal salt, scrypt parameters (`N=16384`, `r=16`, `p=1`, 64-byte output), and `salt:hash` representation. A local sample hash verified in both directions and rejected a wrong password. This supports a **planned** account-hash transfer; it does not prove a remote user migration, OAuth linking, session transfer, or password recovery. Existing sessions should be treated as revoked at cutover, with a fresh Better Auth sign-in and the same app-user ID retained for memberships and authored data. Link only a verified Better Auth identity to an existing app user. [Supported Better Auth plugins](https://labs.convex.dev/better-auth/supported-plugins) do not list API keys as a default-schema plugin and explicitly mark SSO incompatible; inherited PAT and any SSO contract therefore need their own accepted owner before auth retirement.

## Native component choices to prove against current behavior

- [Official Resend component](https://www.convex.dev/components/resend): evaluate for durable notifications and invitations. Current direct Resend sender remains the recovery-sensitive authentication delivery owner until password reset and verification semantics are proven with the component's asynchronous queue.
- [Agent component](https://docs.convex.dev/agents/overview): evaluate for assistant threads/tools/RAG after mapping existing conversation, approval, privacy and cost contracts. Do not duplicate current `assistant/*` storage merely to adopt it.
- [Workpool](https://www.convex.dev/components/workpool) and [Convex cron jobs](https://docs.convex.dev/scheduling/cron-jobs): use when actual job concurrency/retry or recurring schedule requirements demand them; compare each of the 12 Celery entries with the three current Convex crons.
- The listed [MCP gateway](https://www.convex.dev/components/convex-mcp-gateway) is community-maintained and exposes inbound Convex tools. The current `mcp/*` code is an outbound client; these are different contracts. Review gateway auth/security and self-host behavior before adoption.

## Order of closure

1. Establish Better Auth account mapping and one shared session in the preserved shell; accept identity, account, workspace and shell journeys together.
2. Migrate registered legacy routes by family, retaining their dialogs, Power K commands and external API behavior. Update this checklist only after exact browser/role/network evidence.
3. Prove real providers, public/PAT APIs, Celery replacement, remote backup/restore and served deployment. Repeat equivalent performance runs against a resolved control artifact.
4. Confirm no active Django or Postgres consumers, perform rollback rehearsal, then stop the services while retaining recoverable data volumes.
