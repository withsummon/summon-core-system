## Scope and acceptance rule

Every inherited Plane feature remains in scope. The deployed UI is the visual baseline. Each registered route must open under its intended role, complete its reads and writes, exercise its dialogs and commands, show denial/recovery correctly, preserve visible layout and accessibility, and produce a Chrome network capture without Django requests. For external HTTP APIs, compare method, authentication, status, payload, pagination, idempotency, error, and permission contracts with an actual client. For jobs, compare schedule, side effects, retries, and observability. Mark a row accepted only with the exact served build, URL, test actor, artifacts, and rollback record.

The indexed source extraction found **109 web entries** (106 `route`, three `index`) across web/admin/public-space apps, **435 Django endpoint declarations**, ten Django URL mounts, three optional schema/debug declarations, **91 literal Power K command IDs plus two native Stickies commands**, 171 static JSX dialog mounts, **12 Celery beat jobs**, and six Convex crons. All **839 ledger entries** were checked against an existing source file and in-range line and have a nonempty owner and acceptance family. Apply that family's acceptance journey below to the exact pattern or ID in each row; record one artifact per row before changing `OPEN`. The React Router `routes --json` manifest resolves **108 active route/index entries** in either `SUMMON_STICKIES_ROUTE_OWNER` mode; every active path and resolved module matches the ledger, with exactly the alternate `/:workspaceSlug/stickies` module inactive. Run `pnpm exec react-router routes --json` from each of `apps/web`, `apps/admin`, and `apps/space`, and repeat the web command with `SUMMON_STICKIES_ROUTE_OWNER=convex` to reproduce this source-build check. The web `*` routes and Django include mounts are listed intentionally. Dynamic dialogs and keyboard/context actions still need runtime mounted-call review; a local route manifest does not prove the production-served build. The previous 48-pattern Summon list remains a subset of the 435 Django endpoints.

## Better Auth owner migration

The [native account boundary](better-auth-candidate.md) now uses Better Auth component credentials and backing sessions, one React provider, verified identity-to-application-user mapping, native entry/onboarding and preserved account Settings. Existing application user IDs remain stable. Revoked backing sessions deny old JWTs at the product boundary. Sensitive application effects and native credential changes share a Convex mutation; HTTP routes that bypass that transaction are disabled. Local synthetic runtime and built-artifact Chrome evidence are recorded in the boundary receipt, with their limits.

The installed versions are Convex `1.46.0`, Better Auth component `0.12.5` and Better Auth `1.6.33`. Installed Lucia and Better Auth password implementations use compatible canonical scrypt. An operator-only, verified, unambiguous fixture migration retained the app ID and accepted its password. Existing sessions must reauthenticate at cutover. This does not prove real-user credential migration, real email verification/recovery or OAuth linking. Old Convex Auth tables and the mutually exclusive issuer selector remain until rollback and cutover acceptance.

The PAT Settings tab and external `X-Api-Key` boundary remain open. The official API-key plugin requires its own dependency and the component's documented local schema setup; a plugin CRUD tab alone would not migrate `/api/v1/` authentication, permissions, pagination, rate headers or audit behavior. The [React guide](https://labs.convex.dev/better-auth/framework-guides/react), [authorization guide](https://labs.convex.dev/better-auth/basic-usage/authorization) and [local schema guide](https://labs.convex.dev/better-auth/features/local-install) own integration setup. Remote activation remains gated on real identity proof, complete preserved UI journeys and operational evidence.

## Native component choices to prove against current behavior

The [Better Auth candidate boundary](better-auth-candidate.md) separates implemented native account ownership, synthetic runtime proof, development Chrome observations and open cutover acceptance.

- [Official Resend component](https://www.convex.dev/components/resend): evaluate for durable notifications and invitations. Current direct Resend sender remains the recovery-sensitive authentication delivery owner until password reset and verification semantics are proven with the component's asynchronous queue.
- [Agent component](https://docs.convex.dev/agents/overview): evaluate for assistant threads/tools/RAG after mapping existing conversation, approval, privacy and cost contracts. Do not duplicate current `assistant/*` storage merely to adopt it.
- [Workpool](https://www.convex.dev/components/workpool) and [Convex cron jobs](https://docs.convex.dev/scheduling/cron-jobs): use when actual job concurrency/retry or recurring schedule requirements demand them; compare each of the 12 Celery entries with the six current Convex crons.
- The listed [MCP gateway](https://www.convex.dev/components/convex-mcp-gateway) is community-maintained and exposes inbound Convex tools. The current `mcp/*` code is an outbound client; these are different contracts. Review gateway auth/security and self-host behavior before adoption.
