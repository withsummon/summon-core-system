# Operator sign-in policy

The deployed runtime instance projection defaults ENABLE_EMAIL_PASSWORD and ENABLE_MAGIC_LINK_LOGIN to `1`; credential providers explicitly reject `0` (email provider has no explicit default, magic defaults to `1`), so missing values allow both at the provider boundary; the instance database seed instead defaults magic to `0`. Legacy SKIP_ENV_VAR determines database override versus environment. Native configuration remains operator environment owned; migrating stored overrides is explicit, not inferred from the seed.

`identity/signin_policy.ts` owns safe effective password/magic/reset/verification booleans. Password requires literal flag `1` after the runtime default; other nonbinary values fail closed consistently with the public projection rather than preserving the legacy provider/projection inconsistency. magic additionally requires the existing valid Resend configuration. `auth.ts` registers only enabled providers; password reset and verification subproviders exist only with enabled password plus mail. Public mail availability adds passwordSignIn and uses the same effective values. Instance admin configuration and connected-account configuredForSignIn use that owner. OAuth registration and verified-email linking are unchanged.

Unlink now refuses to count a disabled password or magic method as a remaining usable sign-in method. Existing current-password proof may still authenticate a sensitive account action; possession proof is separate from permission to initiate a new password sign-in. Sessions already issued are not automatically revoked by an operator flag change. No live flags, keys or accounts were changed.

Provider registration occurs when the auth module is evaluated. Operator environment changes must be followed by the normal backend reload/deployment evaluation and runtime availability/sign-in verification; source-level environment stubs do not prove a running self-host has refreshed its registration. Do not advertise this receipt as live provider disabling or mail delivery evidence.

Nineteen related policy/account/mail tests pass, including explicit disabled availability, retained default configuration, and rejection of final-provider unlink without deleting account/session state. Backend TypeScript and scoped Oxc are required before commit. Existing production sign-in presentation still needs the new passwordSignIn projection wired; no UI redesign or provider controls were mounted here. No frontend or deployment parity claim is made.
